# Feature Specification: Split Handoff Alignment

**Feature Branch**: `chore/233-align-explicit-issue-split-handoff`

**Created**: 2026-07-07

**Input**: User description: "GitHub issue #233 - Align explicit issue-split handoff with sidecar coordinator format"

## User Scenarios, Technical Outcomes & Testing *(mandatory)*

### Verifiable Technical Outcomes *(use instead of user stories for technical/enabling work)*

- **TO-001**: Explicit issue-split handoff output is compatible with the sidecar coordinator issue format.
  - **Why this priority**: Issue splitting must produce coordinator text that can later enter the opt-in sidecar coordinator workflow without changing normal implementation or planning.
  - **Acceptance Scenarios**:
    1. **Given** a normal issue that the user explicitly asks to split, **When** the split handoff is generated, **Then** the rewritten coordinator issue includes goal, preserved scope, child issues, dependencies, execution model, validation, and out of scope sections.
    2. **Given** child issue text generated by the split handoff, **When** a child is selected for implementation, **Then** the child references the coordinator and remains directly implementable through the normal sequential workflow.
  - **Validation Evidence**: Local sample split rewrite without creating real product issues, plus manual review against the coordinator and child issue template expectations from #223.

- **TO-002**: Explicit split output preserves the #220-#222 routing contract and does not change product scope.
  - **Why this priority**: Split handoff text must not accidentally make parallel execution the default, redo closed child scope during coordinator finalization, or add or remove product requirements.
  - **Acceptance Scenarios**:
    1. **Given** a rewritten coordinator issue, **When** its execution model is reviewed, **Then** it states that coordinator `parallel` execution is opt-in, direct child issues use the normal sequential workflow, and coordinator finalization after all child issues close uses the existing sequential end-to-end workflow.
    2. **Given** a source issue with preserved requirements, **When** the split handoff rewrites it into coordinator and child issue text, **Then** the output preserves the original scope and does not invent additional product behavior or remove requested behavior.
  - **Validation Evidence**: Manual review against the #220 routing contract, #221 guardrails, #222 routing documentation, and #224 PR wording constraints where split handoff text describes delivery.

### Edge Cases

- If the source issue does not contain enough concrete scope to split safely, the handoff must stop or report the missing information instead of inventing seed, foundation, or unrelated child issues.
- If child issues have dependencies, the handoff must record those dependencies and must not imply that hard-dependent work can safely run in parallel.
- If all child issues are closed, the coordinator text must direct finalization through the existing sequential workflow and must not ask Codex to redo closed child issue scope.
- If the user has not explicitly requested issue splitting, the updated handoff instructions must not affect normal specification, planning, implementation, or one-issue/one-PR delivery.

## Requirements *(mandatory)*

### Technical Requirements *(include for technical, architectural, migration, security, operational, refactoring, or enabling work)*

- **TR-001**: The updated handoff instructions MUST apply only when the user explicitly requests issue splitting.
- **TR-002**: Normal CatWorld implementation, planning, and one-issue/one-PR workflow behavior MUST remain unchanged.
- **TR-003**: Rewritten coordinator issue text MUST include goal, preserved scope, child issues, dependencies, execution model, validation, and out of scope sections.
- **TR-004**: Rewritten child issue text MUST reference the coordinator issue and remain directly implementable through the normal sequential workflow.
- **TR-005**: Coordinator issue text MUST follow the #220-#222 routing contract, including opt-in coordinator `parallel` execution and closed-child coordinator finalization through the existing sequential workflow.
- **TR-006**: Coordinator finalization text MUST state that closed child issue scope is not reimplemented during the final pass.
- **TR-007**: Split handoff text MUST preserve the rule that issue splitting does not add or remove product scope.
- **TR-008**: The implementation MUST NOT change `.agents/skills/catworld-implement-issue/SKILL.md`.
- **TR-009**: Validation MUST include a local sample split rewrite without creating real product issues.
- **TR-010**: Validation MUST include manual review against the #220 routing contract and compatibility checks against the #223 and #224 template outcomes.

### Scope Boundaries

- **SB-001**: Feature MUST remain within the CatWorld cat-boarding domain.
- **SB-002**: Feature MUST distinguish implemented behavior from assumptions, exclusions, and unresolved product or architectural questions.
- **SB-003**: Feature MUST NOT introduce cross-species abstractions, multi-tenancy, generic platform claims, or permanent product limits without explicit requirements.

### Out of Scope

- Scanning real issues unless explicitly requested.
- Creating real product issues.
- Implementing sidecar execution.
- Changing normal sequential issue implementation.
- Changing `.agents/skills/catworld-implement-issue/SKILL.md`.
- Adding or removing product scope during splitting.

### Open Questions

- None.
